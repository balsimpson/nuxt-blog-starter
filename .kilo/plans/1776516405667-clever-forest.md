# Convex Agent Plan For Article Generation

## Goal

Replace the hard-coded article generation flow in `convex/posts.ts` with a Convex Agent-based orchestrator that:

1. asks clarification questions when inputs are incomplete,
2. performs web research through Tavily,
3. generates a draft article,
4. refines the draft into review-ready content,
5. preserves the current admin workflow in `app/components/ArticleGenerationWorkspace.vue` as much as possible.

## Current State

### Backend

`convex/posts.ts` currently contains the full session workflow:

1. `createGenerationSession` creates a session and inserts a fixed first question.
2. `addGenerationAnswer` either asks one more fixed question or synthesizes all research/draft/review fields immediately.
3. `approveGenerationSession` creates or updates a draft post and links it back to the session.

This is a synchronous, hard-coded state machine. There is no agent, no external web search, and no resumable orchestration layer.

### Data model

`convex/schema.ts` already has useful tables:

1. `articleGenerationSessions`
2. `articleGenerationMessages`
3. `posts`

These can support the first agent migration without a redesign.

### UI contract

`app/components/ArticleGenerationWorkspace.vue` expects these Convex functions:

1. `api.posts.listGenerationSessions`
2. `api.posts.getGenerationSession`
3. `api.posts.createGenerationSession`
4. `api.posts.addGenerationAnswer`
5. `api.posts.approveGenerationSession`

It renders these session fields directly:

1. `title`
2. `requestedArticle`
3. `status`
4. `stage`
5. `currentQuestion`
6. `outline`
7. `researchSummary`
8. `draftTitle`
9. `draftExcerpt`
10. `draftContent`
11. `reviewNotes`
12. `linkedPostId`
13. `approvedAt`
14. `lastError`
15. `messages`

The lowest-risk path is to preserve this shape and change only the backend implementation.

## Recommended Architecture

### 1. Keep the public UI API stable

Do not force a frontend rewrite. Keep the same session lifecycle functions exposed to the UI, either by leaving them in `convex/posts.ts` or by moving them to a dedicated module and updating the import path in one place.

Recommended public API surface:

1. `listGenerationSessions`
2. `getGenerationSession`
3. `createGenerationSession`
4. `addGenerationAnswer`
5. `approveGenerationSession`
6. optional `retryGenerationSession`

These functions should become thin entry points that:

1. validate input,
2. persist the user event,
3. trigger orchestration,
4. return session identifiers or post identifiers.

### 2. Move orchestration into actions

Agent execution and Tavily calls are network-bound side effects, so they should run in Convex `action`s, not in a mutation.

Recommended flow:

1. `createGenerationSession` mutation inserts session + first user prompt.
2. That mutation schedules or invokes an orchestration action.
3. The orchestration action loads session context, continues the agent thread, and writes the next state.
4. `addGenerationAnswer` mutation inserts the user's reply and invokes the same orchestration action.
5. The action decides whether to ask another question or continue to research/drafting.

### 3. Use Convex Agent for thread memory, not for all domain state

Use the Convex Agent component to persist thread history and tool calls. Keep workflow state in your own tables.

Recommended split:

1. Agent thread stores assistant/user/tool conversation history.
2. `articleGenerationSessions` stores durable workflow state and denormalized outputs for the UI.
3. `articleGenerationMessages` continues to store the user-visible conversation shown in the workspace.

This keeps the agent resumable without forcing the UI to read Convex Agent internals directly.

### 4. Expose narrow tools to the agent

Do not let the model write arbitrary session data. Give it a small set of strongly-scoped tools.

Recommended tool categories:

1. read session context,
2. ask a clarification question,
3. run Tavily search,
4. save research summary,
5. save outline,
6. save draft,
7. save review notes,
8. mark session ready for approval,
9. mark session error.

This makes the workflow more reliable than one broad prompt with unrestricted DB access.

## Proposed File Layout

### Keep or slim down `convex/posts.ts`

After migration, `convex/posts.ts` should either:

1. keep only post CRUD plus thin wrappers for generation APIs, or
2. hand off generation APIs to a new module.

### Add `convex/articleGeneration.ts`

Purpose: public queries and mutations for article-generation session lifecycle.

Recommended contents:

1. `listGenerationSessions`
2. `getGenerationSession`
3. `createGenerationSession`
4. `addGenerationAnswer`
5. `approveGenerationSession`
6. optional `retryGenerationSession`

### Add `convex/articleGenerationAgent.ts`

Purpose: define the Convex Agent instance.

Recommended contents:

1. Agent configuration
2. system instructions
3. model selection
4. tool registration
5. helper for generating or continuing a thread

The agent prompt should explicitly instruct the model to:

1. ask questions only when a missing input blocks good output,
2. gather evidence before drafting,
3. cite or at least preserve source links in intermediate reasoning output,
4. produce structured outputs for research, outline, draft, and review,
5. stop after posting a clarification question when user input is required.

### Add `convex/articleGenerationOrchestrator.ts`

Purpose: action-based orchestration.

Recommended contents:

1. `startSessionOrchestration`
2. `resumeSessionOrchestration`
3. `runSessionTurn`
4. `retrySessionOrchestration`

This module should:

1. load session + messages,
2. create or load the agent thread,
3. invoke the agent,
4. interpret the result,
5. persist normalized outputs via internal mutations,
6. guard against duplicate concurrent runs.

### Add `convex/articleGenerationStore.ts`

Purpose: internal queries and mutations for safe state persistence.

Recommended internal functions:

1. `getSessionContext`
2. `appendSessionMessage`
3. `setSessionStatus`
4. `setCurrentQuestion`
5. `saveResearchOutput`
6. `saveOutlineOutput`
7. `saveDraftOutput`
8. `saveReviewOutput`
9. `markReadyForApproval`
10. `markSessionError`
11. `setActiveRun`
12. `clearActiveRun`

These should be the only write paths used by the orchestrator and tools.

### Add `convex/tavily.ts`

Purpose: encapsulate Tavily HTTP integration.

Recommended contents:

1. search function for broad discovery,
2. optional extract function for fetching a specific page,
3. normalization helpers to map Tavily responses into concise structured results.

Because this is external I/O, Tavily access should be used from an action or from an agent tool backed by an action.

## Schema Changes

### Session table changes

Add the minimum fields needed for orchestration control and thread persistence to `articleGenerationSessions`.

Recommended additions:

1. `agentThreadId?: string`
2. `orchestratorType?: string`
3. `workflowVersion?: string`
4. `activeRunId?: string`
5. `awaitingUserInput?: boolean`
6. `lastCompletedStep?: string`
7. `runCount?: number`
8. `lastAgentAt?: number`
9. `lastUserReplyAt?: number`
10. `errorCode?: string`

Recommended extra index:

1. `by_stage_status` on `['stage', 'status']`

### Message table changes

Keep the existing fields for UI rendering and add a small amount of workflow metadata.

Recommended additions:

1. `step?: string`
2. `agentRunId?: string`
3. `meta?: any` or a stricter object if you want stronger typing

Keep `role`, `kind`, `content`, and `createdAt` so the current UI keeps working.

## Convex Agent Integration Plan

### Dependencies and setup

The repo currently only has `convex` and `convex-nuxt`. It does not yet include the Agent component or Tavily client dependencies.

Implementation should include:

1. adding the Convex Agent component package,
2. adding the model provider package used by Convex Agent,
3. adding a Tavily client dependency or using `fetch` directly from an action,
4. configuring required environment variables.

Expected env vars:

1. `OPENAI_API_KEY` or the provider key for the chosen model
2. `TAVILY_API_KEY`

### Agent behavior

The agent should be defined with:

1. an instruction prompt focused on editor-quality article production,
2. explicit workflow rules,
3. tool access for Tavily and session persistence,
4. stop conditions that prevent runaway tool loops.

Recommended workflow policy inside the prompt:

1. If required context is missing, ask exactly one targeted clarification question and stop.
2. If enough context exists, run Tavily research.
3. Summarize findings into a concise research brief.
4. Produce an outline tied to the intended audience and CTA.
5. Draft the article in markdown suitable for the existing admin editor.
6. Review the draft for gaps, factual weakness, unclear claims, and CTA alignment.
7. Save polished outputs and mark the session `ready_for_approval`.

### Tool design

Recommended tool set for the agent:

1. `getSessionContext`
2. `askClarifyingQuestion`
3. `tavilySearch`
4. `tavilyExtract`
5. `saveResearchSummary`
6. `saveOutline`
7. `saveDraft`
8. `saveReviewNotes`
9. `markReadyForApproval`
10. `markSessionError`

Important design rule: the final UI-facing artifacts should be saved by internal Convex mutations with validated argument shapes, not by letting the agent invent arbitrary fields.

## Tavily Integration Plan

### Recommended usage pattern

Use Tavily as a research tool, not as the entire orchestrator. The Convex Agent should decide when to search and how to synthesize the results.

Recommended staged usage:

1. Search for broad topic coverage and current sources.
2. Extract one or more high-value pages when search snippets are not enough.
3. Synthesize findings into `researchSummary`.
4. Preserve source URLs in the research metadata or the summary so the editor can verify claims later.

### Persisting sources

For the initial version, the simplest approach is:

1. keep `researchSummary` as the UI-visible narrative,
2. store structured source metadata inside a new optional session field or message metadata.

If you want this visible in the UI later, add a dedicated `sources` array to the session model.

## Detailed Execution Steps

### Phase 1. Backend extraction

1. Move generation logic out of `convex/posts.ts` into dedicated article-generation modules.
2. Keep the public API stable so `ArticleGenerationWorkspace.vue` continues to work.
3. Reduce `createGenerationSession` and `addGenerationAnswer` to persistence plus orchestration triggers.

### Phase 2. Schema and state model

1. Extend `articleGenerationSessions` with agent-thread and run-state fields.
2. Extend `articleGenerationMessages` with optional workflow metadata.
3. Regenerate Convex types after schema changes.

### Phase 3. Tavily integration

1. Add a dedicated Tavily action/helper module.
2. Normalize Tavily results into small structured objects.
3. Keep rate-limiting and repeated-search concerns localized in that module.

### Phase 4. Agent definition

1. Install and mount the Convex Agent component.
2. Define the article-generation agent with model, instructions, and tools.
3. Ensure the agent can stop cleanly after asking a clarification question.

### Phase 5. Orchestrator actions

1. Create orchestration actions to start or resume a session.
2. Add active-run guards so one session cannot execute overlapping agent runs.
3. Translate agent outputs into normalized session writes.
4. On failure, set `status = error` and persist `lastError`.

### Phase 6. UI compatibility

1. Keep the visible session fields unchanged.
2. Keep `currentQuestion` as the reply gate for the workspace.
3. Keep `ready_for_approval` as the approve-button gate.
4. Keep `approveGenerationSession` largely unchanged, since it already bridges generation output into `posts`.

### Phase 7. UI improvement for async orchestration

This is the one frontend change worth making during migration.

`ArticleGenerationWorkspace.vue` currently loads the selected session imperatively via `convex.query` in a watcher. With async agent orchestration, session state can change after a mutation returns, so the detail view should ideally become reactive.

Recommended improvement:

1. replace manual selected-session fetching with `useConvexQuery(api.articleGeneration.getGenerationSession, { id })` or the equivalent retained API,
2. keep the rest of the template mostly unchanged.

This is not strictly required, but it will make the workspace update correctly while the agent progresses from research to draft to review.

## Risks And Mitigations

### Risk: asynchronous timing changes the UX

Today the second answer immediately produces a ready draft. After migration, the UI will see intermediate states.

Mitigation:

1. update session `status` and `stage` explicitly,
2. append assistant status messages during progress,
3. keep the view reactive.

### Risk: duplicate concurrent runs

If the user clicks twice or retries while a run is active, two agent runs could write conflicting outputs.

Mitigation:

1. store `activeRunId`,
2. ignore or reject new runs while one is active,
3. clear run state only after completion or failure.

### Risk: incomplete or inconsistent agent output

The current system always creates every UI field. The agent might omit some.

Mitigation:

1. require structured final outputs,
2. validate before saving,
3. only mark `ready_for_approval` after `draftTitle`, `draftExcerpt`, `draftContent`, `outline`, `researchSummary`, and `reviewNotes` exist.

### Risk: factual quality of researched content

Search-enabled drafting increases the chance of unsupported claims.

Mitigation:

1. require multiple sources when possible,
2. keep source URLs in metadata,
3. make the review step explicitly check for unsupported assertions.

## Minimal Acceptance Criteria

The implementation should be considered complete when:

1. a new generation session creates a persistent agent-backed workflow,
2. user replies resume the same session and thread,
3. the agent can ask clarification questions across multiple turns,
4. the agent can call Tavily to research the article topic,
5. research, outline, draft, and review outputs are saved to the existing session model,
6. the workspace displays those outputs without a redesign,
7. approval still creates or updates a draft post in the editor.

## Recommended Implementation Order

1. Add schema fields for agent thread and run state.
2. Extract generation APIs into a dedicated article-generation module.
3. Add internal store functions for session/message writes.
4. Add Tavily integration helpers.
5. Add and configure the Convex Agent component.
6. Implement the article-generation agent and its tools.
7. Implement orchestration actions and concurrency guards.
8. Make the session detail in the Vue workspace reactive.
9. Verify the approve-to-editor path still works.

## Key Design Decision

The most important decision is to preserve the current session/message UI contract and swap only the orchestration engine underneath it. That gives you an agent-driven workflow with Tavily research and refinement while keeping the admin workspace stable and minimizing migration risk.
